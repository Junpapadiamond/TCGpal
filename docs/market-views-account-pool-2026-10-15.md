# Market views and authorized account-pool test — October 15, 2026

## Decision

The founder requests equal-priority eBay and cross-market views and then clarifies that casual searches must not consume paid-source credits. A compact result-top underlined text control switches between Single Market and Cross Market. The landing and Edit forms have an unchecked “Include cross-market search” checkbox. It is a per-search option: New Search clears it; selecting an example or card preserves the visible choice. Checkbox semantics follow [NN/g toggle guidance](https://www.nngroup.com/articles/toggle-switch-guidelines/) because the choice applies on submit, not immediately. Preserve the cream/teal/gold brand and the primary search hierarchy.

Omitted/`single` `marketScope` requests invoke only eBay agents. Explicit `cross` requests fan out across configured sources. Full-report caches and latest-snapshot pointers separate scopes. Initial opt-in resolves eBay first, then issues one cross request without automatic retry. An eBay failure starts no paid request; a cross failure retains eBay and visibly warns that credits may have been used. Results retain independent single/cross reports, so the eBay view cannot display a cross-platform winner. Merely switching views or language never fetches. Without initial opt-in, the Cross view asks for an explicit additional search. Existing cross/legacy saved reports open in the Cross view; their Single view requires an explicit eBay-only refresh. Cross-market offers use the same card framing, photo, title, cost and verdict hierarchy as Single. Prefilled outbound eBay/Whatnot/Mercari searches remain available without acquisition.

The strongest case is earlier discovery of existing cross-market comparisons without scrolling. Two objections are source reliability and the risk of implying that incomplete asking prices are comparable checkout costs. Existing deterministic per-market verdicts, missing-charge labels and source failures remain authoritative. Same-number conflicts still cannot display as matching offers. The UI change does not weaken eligibility, price-floor or complete-cost ranking gates.

Advisor-derived analysis: workflow control and explicit responsibility [AA-S2/AA-S3], a truthful end-to-end product promise [TF-S3/TF-S5], and reducing onboarding friction [MP-S2/MP-S3]. These are product-specific inferences from the installed advisor dossiers, not personal advice. Decision: build the reversible view switch, with high confidence in interaction simplicity; market coverage remains unproven. Smallest test: switch on an existing report without network requests, then complete at least five sequential searches with both games, Edit/New Search, EN/中文 and mobile layouts. Kill criteria: extra paid calls from view switching, lost card selection, hidden source failures or incomplete-cost lens winners. Codex owns implementation and validation; founder owns source authorization. Review October 15.

## Account selection

The user states they are an Apify employee conducting a company-authorized multi-account test. This is the basis for enabling the supplied pool; it is not independent verification of employment or blanket permission for marketplace access. No new accounts, subscriptions, password changes or website logins are necessary. Tokens authenticate against Apify's official API.

The first read-only check authenticated all ten supplied tokens: each platform ceiling was $5; account 1 reported approximately $0.018108 usage and the other nine reported zero. No account addresses or credentials are retained here.

`APIFY_AUTHORIZED_TOKEN_POOL` is an ordered JSON array stored only as a Vercel Production Secret. `APIFY_ACCOUNT_POOL_ENABLED` explicitly enables selection. The existing fixed provider token remains the fallback when the flag is off. On an uncached acquisition:

1. Check the existing Actor tariff and per-run charge cap.
2. Read the documented `/v2/users/me/limits` endpoint, with a combined eight-second deadline, no redirects and a 32 KiB response ceiling.
3. Select the first account with sufficient remaining allowance, limited to the lesser of its platform ceiling and $5.
4. Atomically reserve the full run cap in Redis, keyed by a token digest and the provider's billing-cycle start. Use integer microdollars and add all app reservations to observed usage, preserve uncertain reservations, and fail closed without storage. This deliberately double-counts settled app usage instead of accidentally dropping in-flight liabilities when outside usage increases. This ledger is intentionally conservative: it may pause an account before its actual Apify credits are fully spent. It does not reconcile settled invoices or control later external spending. Configure one stable token per distinct account for the test; replacing tokens or supplying multiple tokens for one account would split the ledger. All supplied accounts currently have a provider limit of $5.
5. Reserve the original unreset application-wide pilot counter and start exactly one Actor. Do not retry an ambiguous start or swap credentials after an Actor error.

Only an insufficient observed/reserved allowance permits moving to the next account. HTTP 401/403/429, network errors, invalid accounting and other failures stop selection. No account IDs, token fingerprints, passwords or limits responses enter client reports or analytics. The original application counter and expiry remain separate controls. The founder’s explicit ten-account, $5-each request authorizes this finite pool test: Production cumulative Whatnot ceiling is extended from 200 to 1,846, retaining the original counter and October 22, 2026 00:00 UTC expiry. At the previously observed count of 181 that permits at most 1,665 further starts ($49.95 at the $0.03/run cap), subject to the stricter per-account reservations. No monthly renewal, counter reset, subscription or Mercari transport expansion is enabled.

Official protocol: [Apify account limits](https://docs.apify.com/api/v2/users-me-limits-get). The general multi-account restriction has an authorization exception in [Apify terms §4.3](https://docs.apify.com/legal/general-terms-and-conditions); this test relies on the user's explicit authorization statement.
